**引言组织：具体问题 → 已有路线为何仍有缺口 → 核心洞察 → 洞察导出的做法 → 关键结果 → 贡献。**

通常 6–8 个自然段，按论证块推进；洞察和方法可以合段，结果可并入贡献。篇幅用于让读者理解“问题为什么成立、改变为什么有价值”。

| 论证块 | 段落内部逻辑 | 优先衔接框架 | 参考占比 |
|---|---|---|---:|
| 问题，1 段 | 研究对象与用途 → 具体困难 → 解决后的价值 | `[研究对象] ... . However, ... .`；只有确有后果才接 `Consequently, ... .` | 10% |
| 已有路线与缺口，1–2 段 | 最相关路线怎么做 → 在何种条件下不足 → 为什么留下问题 | `Existing approaches ... . However, they ... , which ... .` / `While ... , ... because ... .` | 25% |
| 洞察，1 段 | 观察或例子 → 对困难的新解释 → 由此得到的设计方向 | `Our key insight is that ... .` / `We observe that ... . This suggests that ... .` | 15% |
| 方法，1–2 段 | 提出方法 → 关键操作如何利用洞察 → 解决哪项困难 | `Building on this insight, we propose ... . Specifically, ... .` / `To address ... , we ... .` | 25% |
| 结果，1 段或合并 | 评估覆盖什么 → 主要发现 → 为什么支持核心主张 | `Experiments on ... show that ... .`；另一维度用 `Moreover, ... .` | 15% |
| 贡献，通常三条 | 新认识 → 实现方式 → 经验证实的发现 | `Conceptually, ...`；`Technically, ...`；`Empirically, ...` | 10% |

**衔接规范：** 问题与缺口用 `However / While`，原因用 `because`，例子用 `For example`，观察到设计用 `This suggests / Building on`，方法展开用 `Specifically`，证据用 `Experiments ... show`。每个连接只承担其真实逻辑，不在各段重复“挑战很大，因此我们提出”。只有一个挑战时使用单数。

- **缺口要聚焦：** 对比最接近的工作即可，不提前写一篇 Related Work。解释现有方法为何会遇到本文困难，避免“很少有人研究”或笼统“现有方法均不足”。互补或新任务也能构成贡献，不必虚构前人失败。
- **洞察要形成转折：** 用一句可理解的判断将“旧做法为何受限”连到“新做法为何合理”。例如先区分所需信息与表面信号，再解释新的处理方式；不要把组件组合本身称为洞察。动机图或例子放在帮助理解这一转折的位置。
- **方法要讲因果：** 选一到两个关键操作，分别解释它们如何实现洞察。公式推导、完整模块配置与算法步骤留到 Method。
- **贡献要分工：** Conceptually 写认识或问题视角，Technically 写新增机制／性质，Empirically 写证据揭示的结果；不能把同一方法换说法写三次。保留原有方法名。分析、理论、数据集论文按实际贡献调整三条内容，不编造缺失的贡献类型。
- **数字与结束：** 引言通常 1–2 组关键比较即可；结果段与贡献列表避免重复报数。贡献结束后直接进入问题定义，无需另加逐节导航段。只读各段首句，也应能重建主线。
