**方法组织：总体思路 → 按依赖展开的关键机制 → 学习或求解 → 推断与使用。**

开头用一段描述整个方法的过程：引用总览图，按步骤说明方法依次做什么，每一步指向对应小节并说出该小节的实际操作（如 `Section~X computes ... from ...`），不写只有 `Section~X describes ...` 的空导航；方法很长时也可只点出主要新意所在的小节。指向附录的完整算法或例子时用 `provides`、`presents` 等，不用 `gives`。小节按实际计算或论证关系命名。

**小节与总览图一一对应：** 小节标题、段落标题与关键名词和总览图中对应模块的名称一致；图中每个模块用 `(§3.1)` 这类标记注明对应小节，写不下 `Section` 时用 `§`。不在图中呈现的步骤（如训练完成后的迁移或部署）在空间允许时也在图中对应位置加标记，否则在图注中说明。描述训练完成后操作的小节，首句点明这一点（如 `Once ... is trained, we ...`）。

| 内容块 | 内部逻辑 | 参考占比 |
|---|---|---:|
| 总览 | 承接任务目标 → 关键洞察如何改变求解方式 → 主流程与输出 | 15% |
| 核心机制 | 本步要解决什么 → 用已有对象如何计算 → 结果为何有用、交给哪一步 | 50% |
| 学习／求解 | 哪些量未知 → 用什么信号与目标估计 → 如何得到最终参数或解 | 20% |
| 推断／使用 | 新输入经过哪些操作 → 得到什么预测或决策 → 必要资源代价 | 15% |

**每个机制的展开：目的与直觉 → 数学或算法定义 → 作用与衔接。** 先说明为什么需要这一步，再给实现；用上一小节已得到的对象解释下一步，避免反复重新介绍任务。标准组件简述并引用，主要篇幅给真正新增的机制。

- **依赖顺序优先：** 先表示再聚合，先定义量再使用量，先目标再求解。介绍多个组件后用一段、公式或算法把它们合成完整方法；不要留给读者自行拼装。没有训练的算法省去学习块，分析型工作展开分析程序，数据集工作展开构建流程。
- **设计理由就近：** 在读者可能问“为什么这样做”处解释设计所利用的结构、信息或性质。少量动机结果可以辅助说明；完整性能比较、消融和实测效率放 Experiments，不在每个设计后列一段防御性讨论。
- **公式承担计算：** 先说明要计算什么，再给表达式并解释新符号、各项作用及输出用途。区分目标、估计量和近似；同一公式不再用整段逐符号复述。实验超参数的具体取值留给设置。
- **理论承担解释：** 将核心性质放在它支持的设计附近，按“要说明什么 → 条件与结论 → 对方法意味着什么”展开。正文保留关键推理，证明细节和辅助引理放附录。性质若不影响方法理解或主张，可直接放附录，不用定理增加形式感。
- **流程闭合：** 写清哪些量训练、哪些固定，监督或校准信号从哪里来，推断能访问什么，默认方案如何运行；可选变体放主方案之后。核心算法只靠正文应可理解，工程参数与复现细节可查附录。
- **图文分工：** 总览图展示真实数据流，正文解释关键改变及其作用，算法框整理顺序与分支。三者名称和符号一致，小节与图中模块一一对应，不重复维护三套等价解释。

连接词是建议：`To ... , we ...` 说明目的，`Given ...` 承接输入，`This allows ...` 说明作用，`At inference time ...` 切换阶段。读通依赖比连接词丰富更重要。
